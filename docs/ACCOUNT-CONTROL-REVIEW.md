# 账号与任务控制的事务权限 Review

日期：2026-10-19。承接[业务管理写入口审查](MANAGEMENT-WRITES-REVIEW.md)，本轮覆盖后台账号创建、授予/撤销站点权限、停用账号、站点创建、配置事件重试和认证准备重试。

## 问题与修复

上述入口原先有事务外权限检查，但慢请求体、密码哈希或业务锁等待之后，仍可能继续使用撤权前的结果。七个旧实现反例全部失败：五个 HTTP 请求在读取请求体期间移除全局角色后仍返回200；授权和共享建站在业务锁等待期间撤权后仍成功。

修复沿用 `Operators.require` 的事务连接模式，而不是依赖请求开始时的角色快照：

- HTTP 账号创建向既有创建服务传入操作者，密码哈希之后在事务内复查，账号与 `operator.create` 审计一起提交。无操作者的入口只供可信初始化和测试使用，没有增加公开创建接口；HTTP 创建的成员仍不是全局管理员。
- 授予/撤销权限在锁定已有目标授权行后复查。新增授权没有现存行时仍在写入前持有操作者权限，唯一键继续序列化竞争写入。
- 停用账号按 UUID 顺序锁定操作者与目标，再复核权限并修改。使用 `FOR NO KEY UPDATE`，保持与审计等外键的 key-share 锁兼容；相互停用会串行，不能停用自己。
- 共享建站取得账号中心实例锁后复查，独立建站同样在首个写入前复查。站点、配置修订、身份空间/绑定、认证实例和审计仍在一个事务内。
- 两种任务重试先锁定目标记录，再复查权限。认证准备重试增加 `auth.retry` 审计；不是失败状态或目标不存在返回409，重复请求不会悄悄宣称已重新排队。配置事件原有状态限制、租约清除和 `task.retry` 审计保留。

撤权先提交则等待中的操作拒绝，且没有业务或审计写入；操作已经取得事务授权则持有权限到提交/回滚，撤权等待之后生效。合法排队的 worker 任务不会被追溯取消。普通读取没有改成持锁读取。

## 验证范围

新增15项隔离 PostgreSQL 回归：七项旧实现反例、三项额外业务锁等待撤权、密码哈希后复核、两个管理员相互停用、正常账号/授权/停用/两类重试及状态冲突、审计失败回滚，以及已授权重试在审计提交前阻塞撤权。

HTTP 直接经过真实应用路由；慢请求体由受控 ReadableStream 提供，不使用固定延迟猜测读取时机。业务等待通过独立连接锁和 `pg_blocking_pids` 确认。拒绝及回滚用有序行摘要比较账号、授权、站点、身份空间/绑定、配置修订、认证实例、发布事件和审计，避免日志泄露密码哈希或密钥。相互停用验证仅一次成功、另一次403且只生成一条停用审计；不宣称已经证明任意业务组合都不会发生数据库死锁。

新增账号审计只记目标用户标识，不记录初始密码。审计故障注入验证创建账号与认证重试均返回503并完整回滚。提交顺序测试确认撤权确实等待业务事务；事务提交后后续请求被拒绝。
