# 项目开发交接总览

状态核验日期：2026-10-20（2026-10-25 补充状态更新，见“2026-10-25 状态更新”）。本文汇总当前背景、决策、交付进度和后续路线；阶段验收细节以链接的原始记录为准。公开发行门槛以发行 Review 和实际门禁为准，不因阶段功能完成而推定通过。

## 项目背景

本项目面向个人和小团队，目标是用一套应用集中运营多个品牌和域名的导航站。原有 `~/daohang/toolso-ai-open` 包含多个不同定位的导航站，长期按站点配置和页面分支演进，积累了运营经验，也存在配置与站点作用域耦合、页面逻辑重复、跨站内容/账号边界不清、维护改动容易互相影响等问题。新项目独立整理通用能力，支持多站点管理。

用户明确要求重新开发并独立开源，原站群长期保持现状：不迁移线上站点、不改生产、不删除旧代码。只复用经核查可用的经验、代码和测试；受权属/公开规则约束的旧平台代码不直接带入。许可证已选 AGPL-3.0-only。正式品牌已确定为 Qoo.IM Directory；域名和公开仓库名待定。

## 已确认的产品方向

- 面向个人及小团队；首版验证至少三个站点，不把短期容量测试解释成站点上限承诺。
- 运营后台统一管理站点、内容主档、审核和发布；每站拥有独立品牌、域名、配置、分类及发布状态。
- 资源主档与站点发布记录分开。公共内容必须经过统一数据访问层；跨站共享需显式发布，不能绕过可见性检查。
- 配置支持后台编辑和文件协作。AI 可以帮助用户生成页面、模板或配置；生成代码须经过人工审查，模板 SDK 不构成安全沙箱。
- 账号支持独立站点账号空间，也支持共享身份空间；用户数据仍带站点作用域。共享登录采用账号中心/顶层跳转设计，不保证跨域静默 SSO。
- 首个垂直模块选择 GitHub 开源项目目录，按来源同步候选数据，经人工审核后发布。
- 首版为单一应用/集中运维产品，不包括 SaaS 计费、每站独立部署、任意服务端代码在线运行或复杂拖拽建站。

决策依据和旧系统调研见[项目背景](PROJECT-BACKGROUND.md)；产品范围和估算见[开发方案](DEVELOPMENT-PLAN.md)。

## 当前技术与安全边界

代码为 TypeScript/Next.js 模块化单体，使用 PostgreSQL、Better Auth 及独立 worker；数据库写入和权限边界以现有服务层、迁移和测试为准。如仓库存在 `AGENTS.md` 则先读，并检查 `package.json`、相关代码和最新 Review，再决定实现方式。不得凭文档猜接口，也不要覆盖已应用迁移；schema 变化按项目迁移惯例新增。共享身份、站点授权、个人数据和管理员权限分别见[身份设计](IDENTITY.md)、[公共数据访问](DATA-ACCESS.md)和[认证 ADR](ADR-001-AUTH.md)。

模板是可信部署代码而不是沙箱。模板仅可获得已过滤的公开数据，不得直接访问数据库或环境密钥；AI 生成内容上线前需人工审查。配置发布与代码部署是不同流程。未知 Host 应安全拒绝，不得泄漏其他站点信息。备份恢复、权限撤销、任务重试和跨站发布需保留失败/重试证据。

## 建议开发顺序

1. 在本地安全配置 GitHub/Google 测试应用并完成真实浏览器回调联调；记录域名、授权结果、错误路径和证据。先检查 provider 实现和回调 URL，不虚构平台接口。
2. 域名和公开仓库名确定后，核验公开源码候选及完整发布历史并完成最终 Review。发行门禁和外部验收都有真实证据后，才能更新为可发行状态；实际发布需维护者另行明确指令。
3. 按[发行前检查清单](RELEASE-CHECKLIST.md)完成干净 Docker 安装、升级、备份恢复与上线前认证验收；容量工作先明确目标，再做独占资源测试。
4. MVP 之后再讨论自动三方合并、数组语义合并、已有独立账号迁移/冲突解决、跨域静默登录、内置 AI 生成与翻译、更多采集模块、计费和拖拽编辑。这些不是当前已承诺交付。

2026-10-21 代码 Review 后已补：未预期错误日志、邮箱+来源限流、运营者生命周期、生产默认邮箱验证、备份只校验迁移、公开页缓存/robots、GitHub 统计自动更新、`/api/session` 收敛为 `{email, role}`、P0 生产测试入口移除、OAuth 锁池扩大。详见[代码 Review 修复记录](CODE-REVIEW-20261021.md)。

后续每次开发先确认仓库现状和最近 Review，做范围最小的修改，运行覆盖变更面的测试及必要构建；更新相关阶段/专题文档，记录命令、结果和未覆盖项。发行门槛要由可复核材料关闭，不能以反复重跑业务测试替代。
