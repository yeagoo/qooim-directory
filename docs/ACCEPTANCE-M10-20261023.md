## 范围决定

开发前与用户确认：统一的是**来源与任务层**，审核模型保持两套。

- GitHub 是“绑定型”来源：每个来源绑定一个已有主档，候选按主档版本逐字段审核，统计字段自动更新。
- RSS/npm/JSON 是“发现型”来源：发现多条内容，按 `external_id` 去重，接受后生成草稿。

两者的审核语义不同，所以没有把 GitHub 候选并进 `collector_candidate`，以免一张表承载两套语义。

## 迁移与兼容

- **迁移演练**（`tests/p10/migration.test.ts`）：先建一个到 013 为止的数据库，放入各种状态的 GitHub 数据，执行 014 后逐字段核对：
  - 来源：启用和停用两种；ID、配置、版本、间隔、下次运行时间、etag、内容哈希、远端 ID、创建时间都不变；
  - 任务：完成、失败、排队、处理中四种；租约和结果都不变；
  - 候选：待审、已接受、已作废三种；基线版本、应用版本、审核指纹都不变；
  - 请求合并记录不变，旧表已删除；
  - 新约束生效：GitHub 来源必须绑定主档，同一主档只能绑定一个来源；删除任务时，候选保留但 `task_id` 置空，请求合并记录随任务删除。
- **兼容层**：
  - 接口和服务：`/admin/api/github/*`、CLI、`GithubSources` 的输入、权限、错误和返回结构都不变；
  - Worker：`GithubWorker` 和 `CollectorWorker` 的构造函数、返回值、`GithubDelivery` 结构都不变；
  - 页面：后台“开源项目”页没有改动。
- **P4 的 30 项 GitHub 回归**：只把测试里直接写 SQL 的旧表名 `github_task` 改成 `collector_task`（3 处更新加 1 个触发器），断言没有改动。P2 同样只改了表名。

## 新增的共用行为（P10 覆盖）

- adapter 注册表：发现型和绑定型、各自需要的模块、来源显示标签。
- GitHub 来源计入站点来源配额；通用采集接口不能新建、编辑或同步 GitHub 来源（返回 400）。
- 手动同步要新建任务时计入每小时采集次数（超限返回 429），合并到已有的进行中任务不计入。
- 采集任务列表包含 GitHub 任务，失败的 GitHub 任务可以重试（仅站群管理员；同一来源不会出现第二个进行中的任务）。
- 定时调度：每站额度、各来源需要的模块；GitHub 来源已有进行中任务时只顺延下次运行时间，不占额度。
- GitHub 全局限速只约束 GitHub 任务，不会挡住其他类型的任务。
- 保留期：清理旧的 GitHub 任务，以及超期的已作废 GitHub 候选；已接受、已拒绝的候选作为主档变更记录一直保留。
- 采集页：GitHub 行不显示通用的同步/编辑按钮，改为链接到“开源项目”页（浏览器测试）。

## 行为变化（升级说明）

- GitHub 定时同步现在受每站每小时额度限制（默认 60 次），超出的来源推迟 15 分钟；站点正在执行手动同步时，本轮调度会跳过该站。
- 迁移后 GitHub 来源计入站点“采集来源数”配额（默认 20 个）。已经超出的站点只会被阻止新建，现有来源不受影响。
- 被保留期删除的旧任务，其操作 ID 记录也会一并删除；之后重放同一个旧操作 ID 会新建任务。
- 迁移 014 会删除旧表，不能自动回退；升级前请先按 [P5 运维](P5-OPERATIONS.md) 做加密备份。
