# 业务管理写入口的事务权限 Review

日期：2026-10-19。承接[发布与站点状态审查](PERMISSION-TRANSACTION-REVIEW.md)，本轮覆盖八类业务写入口的排队撤权。

## 问题与修复

以下入口原先只在进入事务前检查权限，等待业务锁期间撤权后仍能写入：主档保存、应用主档导入、分类保存、投稿审核、GitHub 来源保存、人工排队、候选审核、登录提供方配置。

现在沿用 `Operators.require` 的事务连接模式，在取得相应资源、分类、投稿、来源、候选或认证实例锁后复核，并持有必要的账号/授权行锁到事务结束。拒绝时不改变主档版本、草稿、审核结果、任务、提供方配置或业务审计。原版本比较、幂等操作标识、模块检查和加密配置保持原样。

主档写入统一在既有私有写入函数中检查全局权限，因此单项保存和批量应用导入都受约束。批量导入第一项获得事务内授权后，权限保持到整批提交/回滚，避免后续项等待时被跨事务改变。没有将只读导入预检改成业务写入。

投稿审核保留既有权限：站点编辑者可接受本站投稿，内部审核路径可以创建对应主档与本站草稿；普通主档保存、导入和 GitHub 审核仍要求全局权限。内部作用域参数不来自 HTTP 请求体，没有开放新的公共接口，接受投稿也不会自动发布。

人工排队在来源锁后复核，包括返回既有任务的幂等分支。已合法排队的后台任务仍遵循原模块、来源版本与租约检查执行，不因为提交者后续角色变化被追溯取消。登录提供方保存同样在认证实例锁后复核，密钥继续加密，提供方版本和审计与配置同事务提交。

并发顺序延用上一轮：撤权先提交则排队写入拒绝；写入先完成事务授权，则撤权等待该事务结束，随后生效。

## 验证设计

八项真实 PostgreSQL 回归在旧实现全部失败，修复后全部通过。各用例先用独立连接持有业务锁，启动操作并通过 `pg_blocking_pids` 确认实际等待；随后撤销编辑授权或移除全局角色并提交，释放锁后检查403。比较所有相关业务表及审计的有序行摘要，验证没有部分写入；不在日志打印私密数据快照。

另有两项正向回归：

- 批量导入两项，阻塞第二项并实际观察全局角色变更等待第一项已持有的权限锁；释放后整批完成，后续主档修改被拒绝。
- 仍获授权的站点编辑者接受本站投稿，生成主档和本站草稿但没有发布记录，且不能绕过全局权限直接保存主档。

使用真实服务层和隔离数据库；投稿、GitHub 候选等准备数据为测试夹具，不调用真实远端平台。已有完整阶段回归另验证实际 HTTP、浏览器、CLI、OAuth及备份恢复路径。
