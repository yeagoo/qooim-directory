# 投稿限流时间边界 Review

日期：2026-10-20。本轮延续 [个人写入会话事务 Review](PERSONAL-TRANSACTION-REVIEW.md)，修复投稿排队后的限流窗口和创建时间。不改变每站每用户每小时最多 10 条的规则、个人 API、正式迁移或依赖。

## 问题与修复

原统计使用 now()，投稿创建时间也采用表默认 now()。PostgreSQL 的这个时间固定于事务开始。请求等待限流锁、身份锁或统计表锁后，即使旧投稿已经退出一小时窗口，仍可能被错误返回 429；新写入的投稿也会被记为排队之前创建。

限流统计现在在 SQL 实际执行时，用 clock_timestamp() 一次采样窗口截止时间。物化 CTE 与标量子查询使本次统计使用同一个截止值，不按每条记录推进时间，也不沿用事务或语句到达时的旧时间。查询继续按 site_id、规范 user_id 和 created_at 范围筛选。

插入显式使用 clock_timestamp() 记录新投稿时间。原每站/用户限流业务锁仍持有到事务提交，多个排队请求不能重复占用第十个名额。前一轮的锁后身份授权、用户/会话共享锁和期限校验保持有效。

统计与插入各自在执行时取数据库时间：额度检查以统计时刻为准，created_at 表示插入时刻。本轮不迁移或推算历史创建时间，不增加应用进程时钟、计数缓存或新的额度表。

## 验证

新增 5 项真实 PostgreSQL 回归：

- 业务锁等待跨过一小时窗口后，原十条已过期，允许新投稿，近期记录只有新的一条。
- 统计表锁等待跨过窗口也按执行时刻判断，防止仅替换为语句开始时间而留下同类问题。
- 投稿创建时间不早于业务锁放行时刻。
- 已有九条时，三个并发排队请求仅一个成功，其余返回 429，记录总数保持十条，且新记录时间正确。
- 同一规范用户在共享账号的另一个站点、以及本站不同用户的额度独立。

最初 3 个反例在旧实现全部失败；修复并扩展后 5 项全部通过。通过真实数据库锁与 pg_blocking_pids 确认请求已排队，先核对事务开始早于窗口边界，再等待短期测试记录退出窗口；不等待真实一小时。测试 finally 释放自建连接上的锁并等待请求结束。

完整回归在生产构建完成后执行，避免重建 `.next` 干扰启动测试。最终 P1/P2/P3/P4 回归 223 项、发行测试 69 项，共 292 项通过；生产构建、类型与依赖边界检查通过。原有 HTTPS/浏览器个人 API 用例继续验证真实请求，本轮新增项为数据库并发测试。未重验 Docker 安装、容量或真实外部 OAuth。
