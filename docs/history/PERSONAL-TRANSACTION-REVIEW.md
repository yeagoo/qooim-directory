# 个人写入的会话事务 Review

日期：2026-10-20。本轮为实现者 Review，修复投稿、添加收藏和取消收藏的会话授权竞争窗口。沿用现有个人 API、身份表、站点隔离及投稿限流，不修改依赖、正式迁移、旧站或后台任务。

## 问题与修复

原投稿先检查会话，再等待本站/用户的限流业务锁。等待期间会话被撤销、用户被封禁或会话到期后，旧校验结果仍能允许写入。个人写入的授权查询也没有持有身份行锁，撤销可能先提交，先前请求随后才写入收藏或投稿。

现在投稿先等待限流业务锁，之后检查身份；排队等待不会占用身份共享锁，退出和封禁可先完成。身份检查按用户、会话顺序获取 FOR SHARE 行锁，核对用户未封禁、会话未撤销、会话属于请求的用户与站点，并持锁直到事务结束。添加及取消收藏复用相同检查。

普通与绝对期限在身份行锁取得后，使用数据库 clock_timestamp() 再次检查。不能使用事务开始时固定的 now()，也不能只在取得身份行锁之前判断期限，否则排队跨过到期时间仍会放行。会话检查失败返回既有 401，不产生业务记录。

提交顺序有两种：撤销或封禁先完成，随后取得授权锁的请求被拒绝；业务请求已持有授权锁，撤销或封禁等待该请求提交或回滚，完成后新请求被拒绝。这里保证撤销与写入的事务顺序，不承诺撤销会取消已经授权的在途事务，也不要求业务提交前重新判断自然到期时间。

现有每站每用户每小时 10 条投稿、可收藏资源可见性和跨站数据隔离协议保持不变。来源于共享账号中心的身份仍由既有认证层先验证；本轮没有改写账号中心或第三方认证流程。

## 验证

新增 10 项真实 PostgreSQL 并发回归：

- 投稿等待限流锁期间，分别提交会话撤销、用户封禁、普通期限到期及绝对期限到期，均返回 401，确认没有投稿记录。
- 已授权投稿、添加收藏、取消收藏与撤销的提交顺序，以及已授权收藏与封禁的顺序：通过 pg_blocking_pids 确认身份修改实际在等待业务事务，随后核对业务行和身份状态，确认后续请求被拒绝。
- 投稿与收藏分别等待身份行锁，自然跨过绝对或普通到期时间；确认请求事务在到期前已开始，但锁释放后仍返回 401，没有新增业务记录。

最初 7 个反例在旧实现全部失败；修复后通过，随后补充到 10 项。测试只控制自建数据库连接、行锁、业务锁和短期会话期限，finally 释放锁并等待自己的请求结束，不借助全局服务重启。

完整 P1/P2/P3/P4 回归 218 项、发行测试 69 项，共 287 项通过。生产构建、类型及边界检查通过。原有真实 HTTPS/浏览器用例继续覆盖登录、收藏、投稿、组退出及审核发布；本轮新增用例直接验证业务服务的数据库事务，没有把它们称为新增浏览器测试。未重验 Docker 安装、容量或真实 GitHub/Google OAuth。

最终源码归档、导出目录与工作区逐文件核对，公开 Markdown 本地链接检查通过。正式品牌、真实 OAuth 联调、4 项依赖许可证材料和 7 项镜像材料仍为发行前置项；门禁保持阻断。
